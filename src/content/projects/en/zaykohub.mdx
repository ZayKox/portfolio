## A personal environment to build

I’m preparing a homelab to bring together personal and family services, practise system administration, and plan hosting for my applications. The repository describes the target architecture, configurations, dependencies, and recovery procedures. No service is currently deployed on the target infrastructure.

The catalogue is a roadmap, not a claim that every service can run simultaneously. Activation will be gradual, based on available resources and tests on the actual hardware.

## Target architecture

Proxmox VE is intended to host three Debian virtual machines running Docker: a foundation for DNS, identity, and access; an environment for private and shared applications; and a separate environment for public ingress and personal projects. Home Assistant OS and Proxmox Backup Server each have a dedicated virtual machine.

This separation aims to limit the consequences of failures or compromise. Public projects must not receive private application data, mounts, or credentials. The design uses one server and makes no claim of high availability or a Kubernetes cluster.

Planned storage separates a 1 TB SSD for systems and application state from a ZFS mirror of two 4 TB hard drives for bulk data. The mirror targets roughly 4 TB usable before filesystem overhead, rather than 8 TB. Mirroring provides redundancy but does not replace independent backups. Hardware compatibility, USB passthrough, and possible graphics acceleration still need qualification.

## Access and data protection

The access model uses default denial and permissions by use case. Administrative interfaces and sensitive applications stay private. Authentik manages homelab identity; Ludosaic and Palimia retain their own product authentication for public users.

Infrastructure secrets are prepared with SOPS and age, then handed off to protected runtime files. Vaultwarden is a planned user service, not the infrastructure bootstrap secret store.

## Backups and recovery

Proxmox Backup Server provides local recovery for selected virtual machine disks. Restic is intended to keep encrypted copies of important data at an independent destination that has not yet been selected. A copy on the same server cannot protect against complete loss of that server.

Procedures pair consistent database exports with their corresponding files. They include integrity checks, recovery of an exact snapshot, and verification of the recovered service before returning it to operation. Recovery keys and instructions must remain accessible without the homelab.

## Work already completed in the repository

Inventories and architecture decisions are versioned. Compose stacks and Ansible roles have been prepared for some services, including identity, observability, file exchange, MQTT, music, and development tools.

Python tools validate metadata, configurations, and execution prerequisites. Isolated rehearsals cover service startup, authentication, anonymous access refusal, permission revocation, and encrypted backup and recovery cycles. Continuous validation checks the artifacts without deploying the homelab. These are local technical results, not validation on the target server.

## Remaining steps and limitations

1. Receive and inspect hardware without changing disks, then qualify storage, peripherals, and the UPS.
2. Install Proxmox, create virtual machines, and verify recovery access.
3. Establish networking, identity, HTTPS ingress, monitoring, and an independent backup destination.
4. Activate applications gradually, measure memory, storage, and heavy jobs, then test recovery on the target environment.
5. Consider public projects after validating domains, capacity, and each application's release conditions.

The initial profile targets 32 GiB of memory, with a planned move to 64 GiB for heavier workloads and both public projects. These budgets are planning assumptions. Capacity testing, connectivity, independent backups, and physical compatibility remain prerequisites for activation.
